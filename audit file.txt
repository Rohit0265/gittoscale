[S-01] CRITICAL — Payment webhook signature bypass via a single header
--------------------------------------------------------------------------------
File: backend/src/routes/payment.ts:170-179

    const allowMockWebhook =
      (process.env.NODE_ENV !== 'production' || process.env.ENABLE_MOCK_AUTH === 'true') &&
      headers['x-mock-webhook'] === 'true';
    let isSignatureValid = false;
    if (allowMockWebhook) { isSignatureValid = true; }
    else { isSignatureValid = verifyPolarWebhookSignature(rawBody, headers); }

Two problems compound:

 a) `ENABLE_MOCK_AUTH` is one global flag. Setting it to 'true' for any reason
    (demo, QA, a mis-set Fly secret) also disables webhook signature
    verification — in production.
 b) When active, ANY unauthenticated POST to /api/payment/webhook carrying
    `x-mock-webhook: true` is accepted as a genuine Polar event and flows into
    handlePolarWebhookEvent(), which grants Pro subscriptions.

The header is not secret, not signed, not IP-restricted. Free Pro on a flag flip.

Fix: the mock branch must require `NODE_ENV !== 'production'` ALONE — never
`|| ENABLE_MOCK_AUTH`. Better: delete the mock webhook path and have tests call
handlePolarWebhookEvent() directly.

[S-02] CRITICAL — Forgeable bearer tokens: `mock_jwt_` is unsigned base64
--------------------------------------------------------------------------------
Files: backend/src/routes/auth.ts:60 (issuance, login)
       backend/src/routes/auth.ts:128 (issuance, signup)
       backend/src/middleware/auth.ts:31, 47-62 (acceptance)
       backend/src/routes/chat.ts:42 (second copy of the same logic)
       backend/src/meeting/yjsServer.ts:64 (third copy)
       backend/src/feed/feedRoutes.ts:50 (FOURTH copy — easy to miss)

    const mockToken = `mock_jwt_${Buffer.from(JSON.stringify({
      id: user.id, email: user.email
    })).toString('base64')}`;

Acceptance is gated on:
    process.env.NODE_ENV !== 'production' || process.env.ENABLE_MOCK_AUTH === 'true'

The gate opens in two situations that are NOT "local dev":
  • NODE_ENV unset or typo'd ('Production', 'prod', empty) — common in
    Docker/fly/systemd misconfiguration. `'Production' !== 'production'`.
  • ENABLE_MOCK_AUTH=true for the payment demo (see S-01).

When open, anyone mints a token for any user id with:
    'mock_jwt_' + btoa(JSON.stringify({id:'<victim-uuid>', email:'x@y.z'}))

That token is accepted by requireAuth and therefore by /api/feed, /api/history,
/api/meetings, /api/payment, /api/chat, /api/admin. Full account takeover of any
user, including admins, from a hand-crafted string. The frontend does exactly
this at frontend/src/services/api.ts:33-37.

Fix: (a) invert the gate — `process.env.ENABLE_MOCK_AUTH === 'true' &&
process.env.NODE_ENV !== 'production'`; (b) HMAC-sign mock tokens with a
server-side secret and verify; (c) deduplicate — the same 20 lines are
copy-pasted in 3 files, so a fix in one place misses two.

[S-03] HIGH — Anonymous identity forgery in the mock OAuth popup
--------------------------------------------------------------------------------
File: frontend/src/contexts/AuthContext.tsx:144-258

When VITE_SUPABASE_URL is unset or a placeholder (services/supabase.ts:6-11
treats '' , 'https://your-project.supabase.co' and any string containing
'placeholder' as "not configured"), signInWithOAuth() contacts no provider. It
builds an HTML page with document.write() into a popup containing:

    function pick(name,email){
      var payload = {type:'GTS_OAUTH_DONE',user:{id:'usr_'+Math.random()..., email:email, fullName:name}};
      window.opener.postMessage(payload, window.location.origin);
    }
    <button onclick="pick('Alex Developer','alex@gmail.com')">
    <button onclick="pick('Dev Tester','dev.tester@gmail.com')">
    <div class="custom" id="customBox">
      <input id="custName"><input id="custEmail">
      <button onclick="submitCustom()">Continue</button>

The user types ANY name and ANY email and is authenticated as that identity,
with a fresh random id, persisted to storage (line 257) and used as the session

[S-06] HIGH — No `trust proxy`, so every client IP is the proxy's IP
--------------------------------------------------------------------------------
File: backend/src/app.ts — verified: no `app.set('trust proxy', ...)`.

Deployed behind Caddy (Caddyfile: reverse_proxy gitoscale:3000) and Fly
(force_https). With trust proxy unset, `req.ip` is the socket peer — the proxy.
Consequences:
  • Any future rate limiter buckets the whole world into one key.
  • Telemetry records one IP for all traffic (middleware/telemetry.ts).
  • The hand-rolled X-Forwarded-For parsing (S-07) is the only thing separating
    users, and that is attacker-controlled.

Fix: `app.set('trust proxy', 1)` (Caddy/Fly both append exactly one hop).

Files: backend/src/routes/chat.ts:358          (getChatClientIdentifier)

[S-13b] MEDIUM — Symlinks are never resolved, so the root restriction is bypassable
--------------------------------------------------------------------------------
File: backend/src/services/staticScanner.ts:150, 164, 173, 186, 192, 437

Verified: the file contains ZERO occurrences of `lstat`, `realpath`,
`isSymbolicLink` or `withFileTypes`. Every directory walk uses
`fs.readdirSync(path)` followed by string-joined child paths.

So a symlink inside the scanned tree — `repo/link -> /etc` — is followed
transparently. The containment check in S-13 runs once on the ROOT path; nothing
re-checks the resolved path of each entry as it is walked. A cloned repo (or a
`localPath` the user controls) containing a symlink reads arbitrary files, and
their contents are returned to the caller and fed to the LLM prompt.

Fix: after resolving each child, `fs.realpathSync` it and re-assert containment
against the root (using the S-13 separator-aware compare). Skip symlinks entirely
unless explicitly allowed, and use `readdirSync(dir, { withFileTypes: true })` so
`dirent.isSymbolicLink()` is available.

[S-13c] MEDIUM — No cap on files read, file size, or total bytes during a scan
--------------------------------------------------------------------------------
File: backend/src/services/staticScanner.ts (inventory walk, ~150-450)

The walk descends 4 levels and reads every file it finds. There is no limit on the
number of files, the size of any single file, or the cumulative bytes read. A
repository containing a 2 GB file, or 200,000 small files, is read into memory in
full and then summarised.

Combined with S-05 (no rate limiting) and S-13b (symlink following) this is a
one-request memory-exhaustion path: point `repoUrl` at a huge public repo, or
`localPath` at a symlink to `/`, and the process allocates until it OOMs.

Fix: cap files (e.g. 5,000), per-file size (e.g. 512 KB, skip larger), and total
bytes (e.g. 50 MB). Abort the walk when any cap is hit and report truncation.

Verified bypasses against `new URL(...).hostname`:
    http://2130706433/          -> hostname '2130706433'      (decimal 127.0.0.1)
    http://0x7f000001/          -> hostname '0x7f000001'
    http://127.1/               -> hostname '127.1'           (2 parts -> false)
    http://[::ffff:7f00:1]/     -> hostname '[::ffff:7f00:1]' (IPv6, never parsed)
    http://169.254.169.254.nip.io/ -> public DNS name resolving to metadata IP

The last one is the important class: the guard inspects the HOSTNAME STRING, then
`fetch()` performs its own DNS resolution. Any attacker-controlled domain with an
A record pointing at 127.0.0.1 or 169.254.169.254 passes the check. There is no
post-resolution verification, so this is a straight DNS-rebinding SSRF.

`POST /api/repository/test-llm` (repository.ts:216) is UNAUTHENTICATED and is the
direct sink: it takes `baseUrl` from the body, calls validateSafeLlmBaseUrl, then
`fetch()`es `baseUrl + '/models'` and returns the status code. That is a blind
SSRF scanner against the internal network and cloud metadata, with a status-code
oracle in the response.

Fix: (a) resolve the hostname yourself (`dns.lookup`), validate the RESOLVED
address against a CIDR list including IPv6 loopback/ULA/link-local, then connect
to that pinned IP (or re-validate in a custom `lookup` passed to the agent);
(b) reject any hostname that is not a registrable public domain unless it is on
ALLOWED_LLM_HOSTS; (c) requireAuth + rate limit on /test-llm.

      inMemoryChatStore: Map                (200 msgs/session, ∞ sessions)

These are fallbacks used when the DB is unreachable — i.e. exactly when the
process is already under stress. Anonymous chat sessions are the worst: keyed by
`anonymous:<client-supplied sessionId>` (S-10), so one client can mint unlimited
entries.

Note: feedbackStore IS capped at 500 (feedback.ts:64) and recommendationCache IS
capped at 50 (recommend.ts:96) — those two are fine.

Fix: cap each store (LRU / max size) and add a sweep timer.

[P-06] MEDIUM — Pagination `limit` is never clamped, and history DOUBLES it
--------------------------------------------------------------------------------
Files: backend/src/routes/history.ts:97, 106, 522
       backend/src/routes/admin.ts:84

--------------------------------------------------------------------------------
[C-01] HIGH — Plan-limit counters are not atomic (double-spend)
--------------------------------------------------------------------------------
File: backend/src/services/subscriptionService.ts:244-284, 286-300
      (same pattern for meetings: 328-364, 366-380)

    const { subscription, usage } = await getSubscriptionAndUsage(userId);  // READ
    if (usage.ai_generation_count >= FREE_LIMITS.AI_GENERATIONS) { deny }   // COMPARE
    const updatedUsed = await incrementAiUsage(userId);                     // WRITE (+1)

Read, compare and increment are three separate round-trips with no row lock and
no transaction. Two concurrent requests both read `used = 2` (limit 3), both pass
the check, both increment — the user gets 4+ generations. This is the exact
mechanism behind the payment test failures in B-01.

Fix: single conditional statement —
    UPDATE public.user_usage
       SET ai_generation_count = ai_generation_count + 1, updated_at = now()
     WHERE user_id = $1 AND ai_generation_count < $2
    RETURNING ai_generation_count;
zero rows returned => limit reached. Apply the same to meeting_creation_count.

[C-02] MEDIUM — Subscription activation is not idempotent across three paths
--------------------------------------------------------------------------------
Files: backend/src/services/polarService.ts:110-129 (token-missing mock path)
       backend/src/services/polarService.ts:270+   (webhook)
       backend/src/routes/payment.ts:203-233       (mock-complete)

Three independent paths call activateSubscription(), and two synthesise their own
ids:
    polarCustomerId:     `cust_mock_${Date.now()}`
    polarSubscriptionId: `sub_mock_${Date.now()}`
A real purchase confirmed via /confirm-checkout AND delivered via webhook can
produce two different polar_subscription_id values for one purchase; the second
overwrites the first, orphaning the real subscription id. Combined with C-01 this
is how plan state ends up wrong in tests.

Also: verifyAndActivateCheckoutSession() (polarService.ts:117-129) activates a
30-day Pro plan when `!token || token === 'mock'` — a MISSING or blanked
POLAR_ACCESS_TOKEN silently grants Pro to anyone who calls confirm-checkout with
a sessionId. Fail-open path in production.

Fix: key activation on the real polar_subscription_id and upsert with
`ON CONFLICT (polar_subscription_id)`. Throw — do not activate — when the token
is absent. Never synthesise ids outside the mock branch.

[C-03] MEDIUM — Feed author identity comes from the request body
--------------------------------------------------------------------------------
File: backend/src/feed/feedRoutes.ts:220-230

    const resolvedAuthorName  = req.body?.authorName  || req.user?.fullName;
    const resolvedAuthorEmail = req.body?.authorEmail || req.user?.email;

A body value always wins over the verified token. Any authenticated user can post

[C-04] LOW — Post length is capped by words, not bytes
--------------------------------------------------------------------------------
File: backend/src/feed/feedRoutes.ts:204-213 (2,500 words), 551 (comments: 1,000 chars)

Posts are capped at 2,500 words with no byte ceiling. 2,500 words of multi-byte
Unicode can exceed 100 KB, and with the 15 MB JSON body limit that value is stored
and re-served on every feed page. Comments are correctly capped by characters —
the two paths are inconsistent.

Fix: add a byte-length cap (~20 KB) on post content.

--------------------------------------------------------------------------------
[C-05] LOW — `useRemoteDb()` ignores whether the DB is configured
--------------------------------------------------------------------------------
File: backend/src/routes/history.ts:17

    const useRemoteDb = () => process.env.NODE_ENV !== 'test';

Named for DB selection, but it only checks NODE_ENV. In test mode Neon is bypassed
even when configured, so tests exercise in-memory paths that diverge from
production behaviour — a plausible contributor to the history/payment test
failures.

Fix: `() => isNeonConfigured() && process.env.NODE_ENV !== 'test'`, and seed the
same store production uses.

--------------------------------------------------------------------------------
[C-06] LOW — Feedback returns 201 before anything durable happens
--------------------------------------------------------------------------------
File: backend/src/routes/feedback.ts:58-78

feedbackStore.push() is a process-local array (capped at 500, good) that is lost
on restart and never read back by any route. The only durable destination is
Telegram. If Telegram is down or unconfigured, the submission is silently dropped
while the API still returns 201.

Fix: persist to the DB and return 201 only after a durable write; treat Telegram
as best-effort.

--------------------------------------------------------------------------------
[C-07] INFO — Route-ordering bug surfaces as a DB error
--------------------------------------------------------------------------------
Evidence from the test run:
    [Meeting] DB fetch warning: invalid input syntax for type uuid: "participants"

A literal string is being passed into a uuid column and the failure is swallowed
into a 500. Express matches routes in declaration order; /:id (line 110) is
registered before /:id/participants (line 162), and nothing validates that
req.params.id is a UUID.

Fix: register literal sub-paths before the parameterised route and validate
`req.params.id` as a UUID at the top of every meeting route, returning 400 for
malformed ids. (See B-01b — same bug, seen from the test side.)
